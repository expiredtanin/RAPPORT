# RAPPORT — Architektur-Übersicht

> Studio-Management für Architekturbüros. Tauri 2.x Desktop-App, React 19 Frontend, Rust-Backend (minimal), localStorage-only Persistierung. Solo-Dev: Karim.
> Dieses Dokument ist die **Karte** der Codebase. Es ersetzt nicht das Lesen einzelner Dateien, soll aber verhindern, dass jede Session bei Null anfangen muss.

---

## 1. Mentales Modell in einem Absatz

RAPPORT ist eine **monolithische SPA**: ein React-Root in [App.tsx](src/App.tsx) hält den **gesamten** App-State in einem `useState({...})`, persistiert ihn synchron in `localStorage` unter dem Key `studio_data_v1`, und übergibt ihn als Props an lazy-geladene Views. Es gibt **kein Routing-Framework** (View-Wechsel via String-State), **kein State-Library** (kein Redux/Context/Zustand), **kein TypeScript**, **kein CSS-Framework** (alles inline `style={{}}` oder ein 700-Zeilen `<style>`-Block in App.tsx). Der **Rust-Teil** ist 109 Zeilen und macht nur drei Dinge: System-Tray, Window-Hide-on-Close, Plugin-Registrierung (Updater, Process, Log). Es gibt **keine `#[tauri::command]`** — Frontend ↔ Backend kommuniziert nur über das Event `rapport:navigate` (Tray → Frontend). Alle Daten sind im WebView-`localStorage`, nichts wird in Rust gespeichert.

**Konsequenz:** Wenn etwas mit Daten passiert, ist es JS. Wenn etwas mit dem Fenster/Tray/Update passiert, ist es Rust. Es gibt keine dritte Stelle.

## 3. Datenfluss — Wie Updates wirklich passieren

```
User-Interaktion in View
     │
     ▼  onChange / onClick
View ruft eine der zwei Props auf:
     │
     ├── update(key, value)      → save(prev => ({ ...prev, [key]: value }))  // Top-Level-Field
     │   update(key, prev => …)    // Variante: Funktion des bisherigen Werts
     └── saveAll(newData)         → save(newData)  // Atomar; auch saveAll(prev => next)
                                     │
                                     ▼
                              dataRef.current = newData; setData(newData)
                              storage.save(newData)   ← Storage-Adapter (Fehler → saveError-Banner)
                                     │
                                     ▼
                              React re-rendert die Hierarchie
```

**Immer auf dem neuesten Stand aufbauen:** `useStudioData` hält neben dem React-State einen `dataRef` mit dem zuletzt gesetzten Stand; `update()`/`save(prev => …)` rechnen darauf. Zwei `update()`-Aufrufe direkt hintereinander (oder einer nach einem `await`, während eine Änderung von aussen hereinkam) überschreiben sich dadurch nicht mehr. In asynchronen Handlern die Funktionsform verwenden (`update("expenses", prev => prev.map(…))`), weil ein vorab aus `data` berechneter Wert veraltet sein kann. `update`/`save` sind stabile Referenzen. Schlägt `storage.save()` fehl (z.B. localStorage voll), zeigt App.tsx `saveError` als Banner über der View, bis wieder ein Speichern gelingt.

**Storage-Adapter** ([src/storage/adapter.ts](src/storage/adapter.ts)) ist die einzige Stelle, die `studio_data_v1` schreibt. Zwei Implementationen mit identischem Promise-Interface:
- `LocalStorageAdapter` — Browser-localStorage; `save()` entprellt (250 ms, wie der Datenordner), `flush()` bei `blur`/`pagehide`/`visibilitychange`. Beenden über Tray oder Cmd+Q wartet, bis `flushStorage()` geschrieben hat (`rapport:quit-requested` → `rapport:quit-ready`, siehe §8); vor dem Neustart nach einem Update schreibt `installAppUpdate` selbst. Nicht abgedeckt: «Beenden» im Dock, Abmelden/Ausschalten (macOS beendet dort direkt) — eine Änderung aus den letzten 250 ms kann verloren gehen (gilt auch für den Datenordner).
- `PocketBaseAdapter` ([pocketbase-adapter.ts](src/storage/pocketbase-adapter.ts)) — Cloud via PocketBase (ein Binary statt Postgres+GoTrue+PostgREST+Kong); pro `data.*`-Array eine eigene Collection (Mapper in [pocketbase-mappers.ts](src/storage/pocketbase-mappers.ts)). Schema/Rules/Hooks liegen im Ordner **`pb/`** dieses Repos. Ersetzt den bisherigen `SupabaseAdapter` (entfernt).
  - **Leere Zahlenfelder:** PocketBase speichert ein leeres Zahlenfeld als 0. Lohnsätze werden deshalb beim Speichern im Mitarbeiter-Dialog, beim Import und beim Umzug in die Cloud ausdrücklich mit den Standardsätzen gefüllt (`withDefaultRates` in utils.ts). Alle Wege, die Mitarbeiter anlegen (Dialog, Import mit Büro-PK-Satz, Einrichtung, Umzug), setzen sie; beim Laden bleibt ein Lohnsatz 0 deshalb 0 (ausdrücklich abgewählt), auch AHV/ALV. Der Mapper liest 0 nur dort als «nicht gesetzt», wo 0 keinen Sinn ergibt: MWST-Satz von Offerte/Rechnung mit MWST (→ Büro-Satz); `defaultPkAGSatz` (→ 8 %). Bei Spesen ist 0 % gültig und bleibt 0.
  - **Feiertage** haben in der Cloud das Datum als Schlüssel und als `id` (ein Feiertag je Datum, der Dialog prüft das). **Rollen für Offerten**: `sort` = Position in der Liste. **Löschen mit Datei** (Belege, Bilder): der Adapter merkt sich den Inhalt vor dem Löschen (`keepBeforeDelete`), «Rückgängig» lädt ihn wieder hoch (nur bei bis zu 3 Löschungen pro Speichern, Sammellöschungen ohne).

Auswahl-Logik beim Modul-Load: `localStorage.rapport_backend` entscheidet (`"local"` | `"cloud"` | `"file"`). Bei Production-Build mit gesetztem `VITE_POCKETBASE_URL` wird automatisch Cloud (für Web-Deploy). Schnittstelle: `hasExistingData()`, `load()`, `save(data)`, `clear()`. PocketBaseAdapter zusätzlich: `signIn/signUp/signOut`, `setStudioId`, `myStudios/listStudios`, `createStudio`, `requestPasswordReset`/`confirmPasswordReset`, `subscribeToChanges`, für den Umzug `writeAreas`/`countArea`. App.tsx zeigt Boot-Spinner ([ViewFallback](src/App.tsx)) bis Initial-Load durch ist.

Alle `data.*`-Entities sind portiert (Studios/Settings/Personen/Projekte aus PB-Phase 1, plus Quotes/Invoices/TimeEntries/Expenses/Employees/Absences/Payroll/Protocols/DeliveryNotes/BlogPosts/Stammdaten aus PB-Phase 2). `load()`/`save()` sind generisch über `ENTITY_MAP`/`CONFIG_MAP` in [pocketbase-adapter.ts](src/storage/pocketbase-adapter.ts) implementiert — neue Entity = neuer Eintrag in einer der beiden Maps + Mapper-Funktion, kein Copy-Paste von Query-Code nötig.

Drei bewusste Vereinfachungen ggü. dem alten Postgres-Schema (siehe Kommentar in [1787424306_phase2_remaining_entities.js](pb/pb_migrations/1787424306_phase2_remaining_entities.js)): `invoice_reminders`, `delivery_note_items` und `project_quote_links` sind als JSON-Felder auf dem Parent-Record statt als eigene Join-Collections abgebildet — das Original war laut SQL-Kommentar ohnehin nur ein 1:1-Abbild von Frontend-Arrays.

Invite-Flow (`inviteMember`) und Seed-Defaults für neu angelegte Studios (Rate-Profile,
Dashboard-Templates, App-Rollen, Absenz-Typen, Brieftemplates) sind portiert — siehe
`invite.pb.js`/`studios.pb.js` in `pb/pb_hooks`.

Passwort-Reset-Confirm-Flow: App.tsx erkennt `#/reset-password/{TOKEN}` im URL-Hash (der PB-Mailtemplate verlinkt dorthin, siehe [pb/pb_migrations](pb/pb_migrations)) und zeigt `ResetPassword.tsx`; `confirmPasswordReset()` im Adapter schließt den Flow ab. Voraussetzung pro Deployment: `APP_URL` in SERVER-CONTAINERs `.env` gesetzt (setzt `meta.appURL` in PocketBase) und SMTP im PocketBase-Dashboard (`/_/` → Settings → Mail settings) konfiguriert — ohne SMTP läuft der Request durch, es kommt aber keine Mail an.

Person-Sharing über Studios hinweg (`personStudioLinks`-Collection, Ersatz für Postgres' `person_studio_links`): eine geteilte Person hat `persons.studio == ""` und ist stattdessen über je eine `personStudioLinks`-Zeile pro berechtigtem Studio sichtbar (Zugriffsregel siehe `pb_migrations/*_person_sharing.js`). Globalisiert wird ausschließlich server-seitig im `create-studio`-Hook (`sharePersonsFrom`-Parameter, UI in `Settings.tsx` → System → "Weiteres Studio anlegen"). `PocketBaseAdapter._syncPersons()` ersetzt dafür den generischen `_syncTable()`-Pfad: `load()` nutzt einen breiteren Filter (lokal ODER verlinkt), `save()` sendet das `studio`-Feld nie bei einem Update einer bereits existierenden Person (nur bei Neuanlage) — verhindert versehentliches Re-Lokalisieren einer geteilten Person beim nächsten Speichern.

**Server-seitige Rollen-/Berechtigungsdurchsetzung** (`pb/pb_hooks/permissions.pb.js`): das App-Rollenmodell (`data.appRoles[].permissions`, siehe [constants.ts](src/constants.ts)) wurde bis dahin NUR im Frontend geprüft (`App.tsx` `userPermissions`/`hasViewAccess`) — die PocketBase-Collection-Rules kannten nur Studio-Mitgliedschaft, nicht die Rolle. Ein Mitarbeiter ohne z.B. `"invoices"`-Berechtigung konnte Rechnungen also per direktem API-Call trotzdem lesen/schreiben. Fünf Record-Request-Hooks (`onRecordsListRequest`/`View`/`Create`/`Update`/`Delete`) prüfen jetzt zusätzlich zur bestehenden `memberRule`, ob die `appRoles`-Rolle des Callers (`permissions === null` = Vollzugriff, sonst Array-Contains) die jeweilige Collection erlaubt — fail-closed bei nicht auflösbarer Rolle/Mitgliedschaft, Superuser-Requests (`e.hasSuperuserAuth()`) bypassen wie bei normalen Rules. Sensible Collections (invoices, quotes, contracts, expenses, internalExpenses, payrollEntries, employees, absences, vacationEntries, overtimeClosings) sind komplett gesperrt (Lesen + Schreiben); quer referenzierte Stammdaten (persons, projects, timeEntries, protocols, deliveryNotes, letterTemplates, studioSettings, studioRoles, dashboardTemplates, absenceTypes, holidays) bleiben für alle aktiven Mitglieder lesbar (viele Views brauchen sie unabhängig von der eigenen Rolle), nur das Schreiben ist gebunden. Wichtige JSVM-Falle dabei: Top-Level-`const`/`function` sind im jeweiligen Hook-Callback zur Request-Laufzeit nicht sicher sichtbar (`ReferenceError: not defined`, gleiches Verhalten wie bei den `routerAdd`-Hooks in `studios.pb.js`/`invite.pb.js`) — die Gate-Map + Rollen-Lookup-Logik ist deshalb in jedem der fünf Callbacks vollständig dupliziert. Ausserdem: `record.get("jsonField")` liefert für ein DB-`null` in der JSVM ein leeres JS-Array statt `null` — die Admin-Vollzugriffs-Prüfung läuft deshalb als `findFirstRecordByFilter`-Filter (`permissions = null || permissions ~ '"<id>"'`) statt über einen JS-seitigen Wertevergleich. Die Record-Request-Hooks decken nur REST ab — PocketBase broadcastet Realtime-Änderungen (vollständiger Record-Inhalt) weiterhin allein über die klassische Collection-ViewRule; ein zusätzlicher `onRealtimeSubscribeRequest`-Hook filtert deshalb Subscription-Topics zu gesperrten Collections aus der angeforderten Liste heraus (Topic-Format `<collectionName>/*?options=<urlencoded JSON>`), statt den ganzen Subscribe-Request abzulehnen (der Client abonniert immer alle Collections auf einmal, siehe `subscribeToChanges()` im Adapter).

**Audit 20.11.2026 (Mandantentrennung, empirisch gegen PocketBase 0.39.11 geprüft):** (1) `studio.studioMembers_via_studio.active = true` ohne `?` hiess «ALLE Mitglieder des Studios aktiv» — ein einziges deaktiviertes Mitglied sperrte das ganze Studio. Migration `1787800000_member_rules_fix.js` stellt alle Regeln auf `active ?= true` um (gleicher Join wie `user ?= …`, gilt also für die eigene Mitgliedschaft) und hängt an jede updateRule mit `studio`-Relation `(@request.body.studio:isset = false || @request.body.studio = studio)` — vorher liess sich ein Datensatz per PATCH in ein fremdes Studio verschieben. (2) `permissions.pb.js`: Der List-Hook prüft zusätzlich jeden gelieferten Datensatz (alle aus dem geprüften Studio), der Realtime-Hook akzeptiert nur noch exakt den Filter `studio = "<id>"` — vorher gab ein Filter wie `studio = "A" || studio = "B"` Nutzern in mehreren Studios Rechnungen etc. aus B, wo ihre Rolle das nicht erlaubt. (3) Registrierung geschlossen (`signup.pb.js`): Konten anlegen nur noch bei der Ersteinrichtung (0 Studios) oder als aktiver Admin eines Studios (Einladen); `create-studio` ebenso (vorher konnte jeder aus dem Netz ein Konto und Studios anlegen). (4) Indizes mit `studio` vorne für absences/vacationEntries/payrollEntries/overtimeClosings, `studioMembers(user)`, `personStudioLinks(studio)` (`1787800100_studio_indexes.js`).

**Audit 24.11.2026 (Rollen in den Regeln, Prüfskript `pb/tests/security-check.mjs`, 34 Prüfungen gegen eine frische Instanz, unabhängiger Gegentest ohne Umgehung):** Die Rollen-Hooks oben greifen nur bei direkten Abfragen der gesperrten Collection; bei `expand`, Filtern über (Rück-)Relationen und Realtime wendet PocketBase nur die Regeln an. Ein Mitarbeiter las so mit `timeEntries?expand=employee` oder `studios/<id>?expand=payrollEntries_via_studio` AHV-Nummern, Löhne und Rechnungen. Neu: `studioMembers.perms` («|recht|…|», Vollzugriff «|*|»), nur vom Server gesetzt (`pb_hooks/memberperms.pb.js` bei jedem Speichern einer Mitgliedschaft und bei Änderungen an `appRoles`), und Migration `1787860000_role_rules.js` hängt die Rechteprüfung an die Regeln (`?~` auf demselben Pfad wie die Mitgliedschaft → gilt für die eigene Zeile): gesperrte Collections Lesen+Schreiben mit Recht; Rollen-Stundensätze, Feiertage, Absenztypen, Dashboard-Vorlagen, Briefpapier nur mit Vollzugriff; `studioSettings` mit «settings», aber Nicht-Admins ändern nur Spesen-/Ausgabenkategorien, Monatsabschluss und Büro-Budget (Hook; IBAN/Adresse/MWST/Mahnwesen nur Admin); `timeEntries` schreiben nur für den eigenen Mitarbeiter-Datensatz (ausser «mitarbeiter»/Vollzugriff); `blogPosts` anlegen/löschen nur eigene, bei fremden nur die eigene Umfrage-Stimme. Ersteinrichtung (0 Studios) braucht den Einrichtungscode `RAPPORT_SETUP_TOKEN` (Header `X-Rapport-Setup`; der Container erzeugt ihn beim ersten Start und schreibt ihn ins Log; CloudSetup/Umzug fragen danach). `create-studio` teilt Kontakte nur aus Büros, in denen der Aufrufer Admin ist. **Konten und Rollen in der Cloud** (E2E 25.11.2026): Der Mitarbeiter-Dialog zeigt im Cloud-Betrieb keinen «App-Zugang» (Passwort/Rolle) mehr und lässt die Verknüpfung `appUserId` unverändert — vorher verlangte er ein Passwort für verknüpfte Personen bzw. trennte ohne Haken das Konto still ab. Einstellungen → Team zeigt pro Mitglied «Mitarbeiter verknüpfen» und «Rolle»; die Rolle ändert der Endpunkt `/api/rapport/set-member-role` (nur Admins, letzter Admin bleibt; `invite.pb.js`). Die Verknüpfung `employees.appUser` setzt/ändert nur Vollzugriff (`integrity.pb.js`). Kontakte/Projekte mit Rechnungen, Offerten oder Verträgen löscht auch der Admin nicht (PocketBase leerte sonst den Kunden in bezahlten Rechnungen; Rückgängig stellte ihn nicht her). Eigene Ferien ohne Vollzugriff speichert «Ferien eintragen» als Antrag; genehmigte eigene Ferien ändert man als Änderungsantrag (approved → pending mit originalData) und kann ihn verwerfen (zurück auf genau originalData), zurücknehmen nur Admin (Migration `1787930000_vacation_change_requests.js`, Prüfskript 126 Prüfungen; originalData prüft der Server gegen den genehmigten Stand und nur aus «approved»; eigene Ferien/Absenzen lassen sich ohne Vollzugriff keiner anderen Person zuordnen und umgekehrt). Ein 404 auf einen noch lesbaren Datensatz gilt im Adapter als Ablehnung (Fehlerbanner + Neuladen), nicht mehr als «schon gelöscht». **Adapter-seitige Fehlertoleranz für RBAC-Antworten** (`src/storage/pocketbase-adapter.ts`): `load()` (ein `Promise.all` über alle Entities) und `_writeSnapshot()` (eine sequentielle Kette von `_syncTable`-Aufrufen pro `save()`) liefen ursprünglich beide komplett ins Leere, sobald der obige RBAC-Hook auch nur eine einzige Collection mit 403 ablehnte — für jede Nicht-Admin-Rolle (r-projektleiter, r-mitarbeiter) brach das Login und jedes Speichern vollständig ab, selbst für Aktionen innerhalb der eigenen Berechtigung. Beide Stellen fangen 403 (Hook-Ablehnung) und 404 (satzbasierte Rule-Ablehnung, z.B. `appRoles.updateRule` seit dem r-admin-only-Fix) jetzt pro Collection ab und behandeln sie als "keine Daten sichtbar" bzw. "Schreiben übersprungen" statt den gesamten Vorgang abzubrechen; andere Fehler (Validierung, Netzwerk, echte Bugs) werden weiterhin durchgereicht.

**Abgleich beim Speichern** (`src/storage/pocketbase-adapter.ts`, Planung in [pocketbase-sync.ts](src/storage/pocketbase-sync.ts)): `save()` bekommt weiterhin den ganzen Datenstand, schreibt aber nur Abweichungen:
1. `_writeSnapshot` überspringt eine Collection ganz, wenn sich `data[key]` seit dem letzten Save nicht per Referenz geändert hat (`_lastData`, zurückgesetzt bei Studio-Wechsel/Logout).
2. Drei-Wege-Abgleich pro Collection gegen `_base` (Stand, der zuletzt mit dem Server übereinstimmte: gesetzt in `load()`/`loadPartial()` und nach jedem erfolgreichen `_syncTable`): gegenüber `_base` unveränderte Zeilen werden nicht geschrieben (fremde, noch nicht nachgeladene Änderungen bleiben erhalten); geänderte Zeilen gehen als Update nur mit den geänderten Feldern (Feld-Merge zwischen zwei Nutzern, Dateien werden nicht bei jeder Änderung neu gesendet, siehe «Dateiablage Cloud»); gelöscht wird nur, was in `_base` war und lokal fehlt (vorher wurden Zeilen gelöscht, die jemand anderes zwischen Speichern und Realtime-Nachladen angelegt hatte). Mit `_base` lädt `_syncTable` vom Server nur `id`/Schlüssel (`fields`), ohne `_base` (Fallback) ganze Zeilen wie früher. Vergleich über `fieldEqual`: leer/null/"" gleich, PocketBase-Mitternachts-Zeitstempel = `YYYY-MM-DD`, JSON unabhängig von der Schlüsselreihenfolge (vorher galt jede Zeile mit Datum als geändert). Natürliche Schlüssel werden gleich angeglichen (Feiertage: Schlüssel `date`; sonst wurde ein geänderter Feiertag neu angelegt → 400 «Value must be unique», gefunden im End-to-End-Test 20.11.2026). Gleiches Feld gleichzeitig geändert → letzter Schreiber gewinnt.
3. Batch-API (`_applyOps`, Chunks à 50, transaktional; serverseitig `1787720000_enable_batch_requests.js`): einzelne Operationen ohne Batch; mindestens 350 ms zwischen zwei Batches und bei 429 einmal warten (Rate-Limit `/api/batch` 3/s pro IP), sonst sequenzieller Fallback. Im sequenziellen Pfad wird ein 404 bei Update/Delete (Datensatz inzwischen weg) nur für diese Operation übersprungen, statt den Rest des Chunks still zu verlieren. Das Rate-Limit `*:create` (20 pro 5 s pro IP) gilt auch für jede Anlage **innerhalb** eines Batches (empirisch gegen 0.39.11: ein Batch mit 50 Anlagen scheiterte immer an der 21., danach einzeln → 429): `_chunkOps` nimmt höchstens 20 Anlagen pro Batch, `_reserveCreates` hält ein gleitendes Fenster über alle Anlagen des Adapters (Batch, einzeln, Uploads). Viele neue Datensätze (Umzug, Import) gehen damit mit höchstens ~4 Anlagen/s.
4. Vorübergehende Fehler (Netz weg, 429, 5xx) wiederholt `save()` nach 1/3/10 s; danach Fehler wie bisher (`saveError`-Banner). Der nächste Save schreibt alles seit dem letzten erfolgreichen Stand nach.
5. Realtime-Refresh (`subscribeToChanges` → data-Key, `loadPartial()` im 500-ms-Debounce, Tab-Fokus und `online` → voller `load()`). `useStudioData` wartet vorher auf laufende Schreibvorgänge (`whenIdle()`) und verrechnet gegen `syncedRef` (letzter sicher gespeicherter Stand: geladen, von aussen übernommen, erfolgreich gespeichert): Keys, die seither lokal geändert wurden — während des Ladens getippt, offline oder nach einem Speicherfehler —, bekommen `mergeValue` statt des Serverstands, und das Ergebnis wird gleich neu gespeichert (vorher sprang eine offline gemachte Änderung beim Wieder-online-Gehen still zurück; Test gleichzeitiges Arbeiten 25.11.2026). Schlägt der erste Realtime-Verbindungsaufbau fehl, abonniert der Adapter mit wachsender Wartezeit (5–60 s) neu und lädt danach einmal voll nach. Nach dem Laden markiert `markSynced` den Stand, damit das erste Speichern nur Geändertes abfragt. `save()` sammelt 250 ms (`SAVE_DEBOUNCE_MS`), Tippen wird so ein paar Anfragen statt einer pro Taste; solange noch geschrieben wird (`isBusy`), fragt der Browser beim Schliessen nach. `users` aktualisiert nur der volle Reload.
6. **Bearbeiten-Fenster** (Rechnung, Offerte, Projekt + Projekt-Einstellungen/Budget, Firma, Büro-Einstellungen) speichern über `applyEdit(original, bearbeitet, aktuell)` (merge.ts): nur was im Fenster gegenüber dem Stand beim Öffnen geändert wurde, überschreibt den aktuellen Datensatz; abgeleitete Summen danach neu rechnen (Offerte: Inhalt mit Summen als Block — aus dem Fenster, wenn dort am Inhalt etwas geändert wurde, sonst der aktuelle). Vorher schrieben sie die beim Öffnen kopierte Fassung zurück und setzten fremde Änderungen zurück (Status «gesendet» → «entwurf», Telefon, Monatsabschluss). Neue Bearbeiten-Fenster bitte genauso. Ebenso Protokoll-Detail (Basis = Stand beim Öffnen/letzten Speichern; ändert sich das gespeicherte Protokoll, werden die eigenen Eingaben darauf übertragen, damit Anzeige, PDF und Folgesitzung fremde Punkte enthalten), Lieferschein, Mitarbeiter, Spese, Ausgabe, Vertrag, Lead und Pinnwand-Beitrag bearbeiten; alles, was nach einer Rückfrage (`askConfirm`) oder einem `await` (Passwort hashen, Dateien lesen) speichert, über `prev =>` (Audit Runde 22). Bekannte Grenze: das Terminprogramm eines Projekts ist ein Feld — bearbeiten zwei Personen gleichzeitig dasselbe Programm (auch Rückgängig/Wiederholen), gewinnt der letzte Stand (Cloud-Test Runde 21: ein länger offenes Fenster verwarf fremde Änderungen). Die Mahnung liest die Rechnung aktuell (nicht als Momentaufnahme) und mahnt keine inzwischen bezahlte bzw. keine Stufe doppelt; eine vom Server abgelehnte neue Rechnung (Nummer gleichzeitig vergeben) öffnet sich mit neuer Nummer wieder im Editor; Dashboard-Vorlagen speichert in der Cloud nur Vollzugriff (die Übersicht bietet sie sonst nicht an). Offen: gleichzeitige PATCHes auf verschiedene Felder desselben Datensatzes können sich auf dem Server überschneiden (PocketBase schreibt den ganzen Datensatz; Fenster: Bearbeitungszeit auf dem Server).

- **Speichern:** `PbFileStore` merkt sich `data:`-URL ↔ Verweis; `_toRows`/`toRefs` setzen für bekannte `data:`-URLs den Verweis ein, Server-Zeilen bringt `fromRecord` auf dieselbe Form → im Drei-Wege-Abgleich (`_base`) stehen kurze, stabile Verweise, unveränderte Dateien werden nie erneut hochgeladen. Neue `data:`-URL (Upload in der App, Import eines JSON-Backups, `storage.save(imported)`) → `prepareBody` macht ein `File` daraus, die Operation geht **einzeln als multipart** (nicht im Batch), bei 429 (Rate-Limit `*:create` 20/5 s, z.B. Import vieler Belege) bis zu dreimal nach 1.1/2.5/5 s wiederholt; danach gilt der neue Verweis. Leerer Wert entfernt die Datei; Verweis auf einen anderen Datensatz (kopierte Zeile) wird heruntergeladen und neu hochgeladen; fremde Werte (z.B. `rapport-datei:`) werden nicht gesendet. Dateiname = Originalname (`receiptName`/`name`, sonst `beleg`/`logo`/`bild`), PocketBase hängt ein Zufallssuffix an.
- **Rechte:** alle Dateifelder `protected: true` → Download nur mit Datei-Token eines Nutzers, der die viewRule erfüllt (aktives Mitglied des Studios); ein Nutzer eines anderen Büros bekommt auch mit eigenem Token 404. Belege zusätzlich rollengebunden (`onFileDownloadRequest` in `permissions.pb.js`, Nutzer aus dem Datei-Token — `e.auth` ist dort leer). Logo/Bilder/Dokument-Design sind für alle Mitglieder ladbar (jeder druckt).
- JSON-Backup (Einstellungen → System) bettet Belege über `cloudStorage.embedAttachments` ein; nicht ladbare bleiben Verweis. Fehlt eine Datei (iCloud noch nicht geladen), bleibt der Verweis stehen (`missingFiles`, als Hinweis in der App) und wird unverändert zurückgeschrieben. Verweise ausserhalb von `Dateien/` (`..`) werden nie gelesen. Der JSON-Export in den Einstellungen enthält die Anhänge weiter eingebettet (eigenständiges Backup).

Rust: `tauri-plugin-fs` (+`watch`), `tauri-plugin-dialog`, `tauri-plugin-persisted-scope` — der Dialog erweitert den fs-Scope zur Laufzeit auf den gewählten Ordner, persisted-scope behält ihn über Neustarts; Capabilities `dialog:allow-open`, `fs:allow-*` (auch `read-file`/`write-file` für die Dateiablage) und als einziger statischer Pfad `fs:scope` auf `$DOCUMENT/Rapport` (Standard-Rapport-Ordner, ohne Dialog angelegt). **Nicht enthalten:** Verschlüsselung, Rechte (wer den Ordner lesen darf, sieht alles; Rollen gelten nur in der App). Wechsel zurück zum lokalen Speicher gibt es nicht (der alte localStorage-Bestand bleibt unverändert stehen).

**Umzug in die Cloud** ([cloud-migrate.ts](src/storage/cloud-migrate.ts), Dialog [settings/CloudMigration.tsx](src/views/settings/CloudMigration.tsx), Einstellungen → System → «Daten in die Cloud übertragen…», nur Admin, nicht im Server-Modus): lokal (localStorage) oder Datenordner → ein Büro auf einem PocketBase-Server. Ablauf: Server-Adresse → leerer Server: Admin-Konto + Büro anlegen (wie CloudSetup), sonst mit Cloud-Konto anmelden und neues Büro anlegen (nur Admins, `create-studio`) oder ein bestehendes Büro wählen, in dem man Admin ist → Prüfen (`planMigration`: Bereiche mit Anzahl; Bereiche ohne Cloud-Speicher wie `leads`/`activities` werden genannt und nicht übertragen; ungültige/doppelte Ids blockieren; Datenordner-Anhänge, die nicht gelesen werden konnten, werden genannt) → `checkTarget`: ein Büro mit Daten (Vorgaben eines neuen Büros zählen nicht, `SEEDED_AREAS`) wird nur nach eingetipptem «ÜBERSCHREIBEN» ersetzt, sein bisheriger Stand wird vorher als JSON heruntergeladen → automatisch vollständiges Backup (JSON inkl. Belegen, wie «Backup als JSON») → `runMigration`: Bereich für Bereich über `PocketBaseAdapter.writeAreas` (Full Replace ohne Abgleichsstand, 403/404 hier ein Fehler), Reihenfolge `CLOUD_DATA_KEYS` (Relationen), vorübergehende Fehler werden wiederholt, «Abbrechen» wirkt zwischen zwei Bereichen; danach immer Prüfung Anzahl lokal vs. Cloud je Bereich (`countArea`), auch nach Abbruch/Fehler. Ein erneuter Lauf ins selbe Büro legt nichts doppelt an. Datenordner: `fileStorage.embedAttachments` macht vorher aus `rapport-datei:`-Verweisen `data:`-URLs, die `pocketbase-files.ts` hochlädt. **Ids bleiben erhalten** (`uuidIdField`: freier Text `^[a-zA-Z0-9-]{1,64}$`), damit Verweise stimmen — sie sind aber serverweit eindeutig: dieselben Daten ein zweites Mal in ein anderes Büro desselben Servers scheitern (Meldung mit Feld). **Benutzer:** lokale Konten (PBKDF2) lassen sich nicht übernehmen; der Admin bekommt sein Cloud-Konto (`employees.appUserId` seines Mitarbeitenden zeigt darauf, alle anderen werden leer), die übrigen Benutzer landen in `rapport_cloud_invites` und erscheinen in Einstellungen → Team als «Aus dem Umzug noch einzuladen» (Einladen setzt die Verknüpfung zum Mitarbeitenden; der Einladen-Dialog hat dafür allgemein ein Feld «Mitarbeiter/in verknüpfen»). **Umstellen** erst nach erfolgreicher Prüfung: `rapport_backend=cloud`, `rapport_cloud_url`, `rapport_080_recovery` (sonst setzt die 0.8.0-Regel den Wechsel zurück, solange lokale Daten liegen), Sitzung (`rapport_user`, `rapport_studio_id`) wird direkt übernommen. Die lokalen Daten werden **nicht** gelöscht (localStorage `studio_data_v1` bzw. Datenordner bleiben als Sicherung; Hinweis aus `rapport_cloud_migrated` in Einstellungen → System). Dauer: wegen `*:create` 20/5 s etwa 4 neue Datensätze pro Sekunde (2500 Zeiteinträge ≈ 11 min).

**Per-Device-UI-State** (Dark Mode, Zoom, Sidebar-Collapse, Changelog-Seen, `rapport_backend`/`rapport_cloud_url`) bleibt außerhalb des Adapters in direktem `localStorage` — kommt nicht in die Cloud.

**Schema-Migrations** ([src/storage/migrations.ts](src/storage/migrations.ts)) sind als reine Funktion `applyMigrations(raw, defaultData)` extrahiert, damit derselbe Code auf Local-, Ordner- und Cloud-geladenen Daten läuft. Beim Initial-Load (und bei jedem Nachladen) wird das Ergebnis vom Adapter durch diese Funktion gepiped, bevor es in `useState` landet. Als Erstes prüft sie die grobe Form ([validate.ts](src/storage/validate.ts)): Liste/Objekt/einfacher Wert vertauscht (oberste Ebene und `settings`) → Default; Listeneinträge, die keine Objekte sind → verworfen; Unterlisten, auf die Ansichten ohne Absicherung zugreifen (`NESTED_LISTS`: Rechnungspositionen, Mahnungen, Traktanden, Projektpositionen …) → keine Liste wird leere Liste; Zahl vs. Text gilt nicht als Fehler. Gefundenes landet als `console.warn` und über `onProblems` in `dataNotices` von `useStudioData` → Hinweis oben im Inhalt (App.tsx, «Ausblenden» merkt sich den Text bis zum Neustart); fehlende Anhänge im Datenordner ebenso.

**Wichtig:**
- `save()` setzt den React-State sofort; localStorage und Datenordner schreiben entprellt (250 ms), die Cloud nur Abweichungen (siehe oben).
- localStorage: **kein Backup, kein Abgleich**. Zwei Browser-Tabs im Testmodus überschreiben sich gegenseitig (letzter gewinnt); die Desktop-App hat nur ein Fenster. Tagesbackups und Drei-Wege-Merge gibt es nur im Datenordner, Abgleich nur dort und in der Cloud.
- Datenordner: Nachladen einer fremden Änderung (`checkExternal`) läuft in derselben Kette wie das Speichern; wird während des Ladens in der App geändert, meldet es nichts, sondern das ausstehende Speichern verrechnet beide Stände und meldet danach den gemeinsamen (vorher konnte dabei die fremde Änderung überschrieben werden).
- Backup importieren (Einstellungen → System) prüft die Datei vorher (`checkBackup` in validate.ts: Datenobjekt mit `settings`, lokal mindestens ein Benutzer mit Passwort) und speichert sie migriert. Im Cloud-Modus (nur Admin) läuft das Backup stattdessen durch den Umzugsdialog («Backup in dieses Büro übertragen», siehe «Umzug in die Cloud») — Leer-Prüfung des aktiven Büros, Fortschritt, Prüfung.
- Formprüfung beim Laden (validate.ts) bis eine Ebene in die Listeneinträge (Unterlisten aus `NESTED_LISTS`); einzelne Felder (z.B. `invoice.total` als Objekt) werden nicht geprüft — solche Fehler fängt nur der Error-Boundary der Ansicht ab.

**`data` Top-Level-Struktur** (definiert in [constants.ts](src/constants.ts)):
```
{
  settings,           // Studio-Daten: Name, IBAN, MWST, Stundensätze, Rollen, …
  persons[],          // Kontakte (UI: «Kontakte»); Kategorie `category`, keine Auftraggeber/Partner-Filter mehr
  projects[],         // Projekte mit SIA-Phasen / Budget / Billing-Type
  timeEntries[],      // Stundeneinträge
  invoices[], quotes[],
  expenses[], internalExpenses[],
  employees[], absences[], ferienEntries[], lohnEntries[],
  protocols[], deliveryNotes[], letterTemplates[],
  dashboardTemplates[], appRoles[], users[]
}
```

**Kontakte:** `Person.category` (`person | unternehmer | oeffentlich | auslober | wbw`, Labels in `CONTACT_CATEGORIES`) wird beim Erstellen gewählt. Die Altflags `isAuftraggeber`/`isPartner` bleiben im Datenmodell (Cloud-Zuordnung, alte Daten), **filtern aber nichts mehr**: jeder Kontakt ist in Offerten, Rechnungen, Projekten und Verträgen wählbar. Altdaten ohne `category`: ehemalige Partner gelten als «Unternehmer» (`contactCategory()` in utils.ts), alle anderen sind ohne Kategorie. Die Kategorie ist in der Cloud-Zuordnung (Feld `category`, PB-Migration `pb/pb_migrations/1787740000_person_category.js` — muss auf dem Server eingespielt sein, sonst scheitert das Speichern von Kontakten). Herkunft, Empfehler und Tags (Akquise, Testbetrieb) sind weiter nur lokal.

**CRM / Akquise** (`leads[]`, `activities[]`, plus `Person.source/referredById/tags`, `settings.leadSources`):
- `Lead` = ein Akquise-Vorgang mit Stufe (`anfrage` → `besichtigung` → `offerte` → `verhandlung` → `gewonnen` | `verloren`), Herkunft, Empfehler (`referrerId`), geschätztem Honorar (netto), optional verknüpfter Offerte/Projekt. `Activity` = Kontaktverlauf einer Person (mit optionaler Wiedervorlage); Meetings werden daraus gezählt, nicht gespeichert.
- Auswertung nur in [crm.ts](src/crm.ts), nichts Aggregiertes wird gespeichert. «Umsatz» = netto nach Rabatt (`invoiceNet`), alle Rechnungen ausser Entwurf, nach Rechnungsdatum. Empfehler/Herkunft einer Rechnung: Lead (über Projekt oder Offerte) vor `Person.referredById`/`Person.source`.
- Zahlungsmoral braucht `Invoice.paidDate`; die UI setzt es seit dem CRM-Update beim Wechsel auf «bezahlt» (ältere Rechnungen haben keins).
- **Nur lokal:** `leads`/`activities` sind noch nicht in `ENTITY_MAP` des PocketBase-Adapters. Im Cloud-Modus werden sie nicht synchronisiert. Für den Sync: ENTITY_MAP + Mapper (`pocketbase-mappers.ts`), Collections und Gate-Listen in `pb/` (Migration + `pb/pb_hooks/permissions.pb.js`).

## 4. Navigation & State-Verwaltung

**Navigation** ist eine String-State-Machine in [App.tsx](src/App.tsx):
- `const [view, setView] = useState("dashboard")`
- Jede View ist ein String-Identifier (`"dashboard"`, `"projects"`, `"time"`, …)
- `navigate(newView)` schiebt auf einen Ref-basierten History-Stack (Browser-ähnliches Vor/Zurück)
- Drill-down via `selectedProjectId` etc. (zweiter State neben `view`)

**Modals:** Inkonsistent — manche Views nutzen `modal: { type, id }`, andere haben mehrere separate `useState` (siehe [Invoices.tsx](src/views/Invoices.tsx): `setModal`, `setNewInvModal`, `setAkontoModal`). Es gibt keinen zentralen Modal-Manager.

**Sessions/Auth:**
- `sessionStorage.rapport_user` — angemeldeter User (gestrippt von Credentials)
- Login per PBKDF2-SHA-256 (600k Iter seit 24.11.2026, Rundenzahl im Salt `i600000:<hex>`; Salt ohne Präfix = alte 100k, 16-Byte Salt) — siehe `hashPassword`, `verifyPassword` in [utils.ts](src/utils.ts); kein Standardkonto mehr in `defaultData.users` (vorher «admin»/«admin»), Backup-Import in der Einrichtung nur mit Benutzern (`checkBackup`)
- Lockout: 5 Fehlversuche → 60s Sperre ([Login.tsx](src/views/Login.tsx))
- Auto-Upgrade: Klartext-Altbestand und Hashes mit alter Rundenzahl werden beim ersten erfolgreichen Login neu gehasht (`needsPasswordUpgrade`, [App.tsx](src/App.tsx))

### Rechnungen (Regeln, Stand 26.11)

- **Summen** (`calcTotal`): jede Position (`lineAmount`, auch freie Offert-Positionen), Zwischentotal, Gesamtrabatt, Netto nach Rabatt (`subAfterDisc`) und MWST je auf Rappen gerundet (kaufmännisch, `roundCHF`: x.xx5 auf, Gutschriften spiegelbildlich), Total = Netto + MWST. Gespeichert beim Speichern, danach nur angezeigt (alte Rechnungen werden nicht neu berechnet, erst beim nächsten Speichern). PDF «Netto» = `invoiceNet`, QR-Betrag = `total`.
- **Nummer** (`nextInvoiceNumber`): Jahr/Monat aus dem Rechnungsdatum, laufende Nummer pro Jahr; bei einer neuen Rechnung folgt die automatisch vergebene Nummer einer Datumsänderung. Speichern mit einer schon vergebenen Nummer wird abgewiesen (Meldung). Der Akonto-Planer vergibt die Nummern nach dem Datum jeder Rate.
- **Dialog «Neue Rechnung»**: Startmodus nach Abrechnungsart (`defaultInvoiceMode`: Pauschal → Akonto % vom Honorar, Stundensatz → Teilrechnung nach Stunden), auch aus dem Projekt-Arbeitsraum. Layout wie der Editor (`Modal` mit `preview`, breit; Vorschau ab 1200 px Fensterbreite offen wie im Editor, `previewFrom`): rechts die Live-PDF-Vorschau (`LivePreview`) aus genau dem Formular, das «Weiter» erzeugt (`buildNewInvoiceForm`, mit der nächsten Rechnungsnummer), im Fuss Art, Netto, MWST und Total. Im Projekt-Reiter der Stand der Verrechnung (`projectBillingStatus`: Honorar, bisher gestellt in CHF und % ohne Entwürfe, Rest, offene Entwürfe separat, «= Rest übernehmen») und für Akonto/Teilrechnung der Stand nach dieser Rechnung; über 100 % des Honorars eine Warnung, nur zusammen mit offenen Entwürfen ein Hinweis. «Weiter» bleibt gesperrt, solange Projekt/Offerte oder (nach SIA-Phase) die Phase fehlt.
- **Zeiteinträge**: nur Rechnungen nach Stunden (`hoursFromEntries`: Teilrechnung/Akonto/Schluss nach Stunden, Autofill eines Stundensatz-Projekts, Bearbeiten einer Rechnung mit verknüpften Einträgen) zeigen die Auswahl; Zeile 1 = gewählte Stunden × Satz folgt nur Änderungen an der Auswahl. Betrag-, %- und Phasen-Rechnungen markieren keine Einträge und werden nicht überschrieben. Die verrechneten Minuten je Eintrag bleiben in `Invoice.entrySelections` (bestehendes Cloud-Feld) und werden beim Bearbeiten wieder geladen.
- **Schlussrechnung**: Pauschal = `projectFee` minus alle gestellten Rechnungen des Projekts (netto nach Rabatt, ohne Entwürfe; eine frühere Schlussrechnung zählt mit, damit eine zweite nach einem Nachtrag nur die Differenz stellt). Stundensatz = offene Stunden bis heute minus Akonti/Teilrechnungen, die nicht nach Stunden gestellt wurden. Aus einer Offerte = `Quote.sub` minus die Rechnungen dieser Offerte (`invoicesForQuote`: `quoteId`, bei der Hauptofferte zusätzlich Projekt-Rechnungen ohne Offertbezug; Nachträge getrennt).
- **Teilrechnung «Nach SIA-Phase»**: offerierter Phasenbetrag aus den verknüpften Offerten (`phaseInvoiceAmount`; Aufwand-Offerten mit den Sätzen der Rollen), ohne Offerte Phasenstunden × Stundensatz.
- **Akonto-Planer**: höchstens 24 Raten (Betrag durch die tatsächliche Anzahl, die letzte Rate gleicht die Rappen aus), Vorschlag = Restbetrag (`projectFee` minus gestellte Rechnungen), «= Budget übernehmen» als Alternative. Verteilung «Nach SIA-Phasen» (`akontoPhasePlan`, nur mit Phasenbudget): je Phase mit Stunden (SIA-Reihenfolge) der Anteil am Honorar = `phaseInvoiceAmount` im Verhältnis zur Summe der Phasenbeträge, umgelegt auf `projectFee` (ohne Honorar die Phasenbeträge selbst, Rappenausgleich in der letzten Phase); bisher gestellte Rechnungen (ohne Entwürfe) werden den Phasen der Reihe nach angerechnet, gedeckte Phasen erscheinen als «gestellt», die Raten ergeben genau den Rest. Datum je Phase: ab «Erste Rechnung» im Monatsabstand, einzeln änderbar; Phasen abwählbar. Positionstext «Akontorechnung ‹Phase› – Projekt» (erkennt auch «Nach SIA-Phase» im Dialog «Neue Rechnung» als verrechnet).
- **Abrechnungsblock** (`invoiceBillingSummary`, nur Akonto/Teilrechnung): im PDF unter den Summen «Stand der Abrechnung (netto, exkl. MWST)» mit Honorar total, bisher in Rechnung gestellt (mit Nummern), diese Rechnung und Rest (über dem Honorar: «Über dem Honorar nach dieser Rechnung», positiv), je mit % des Honorars. Basis: mit `quoteId` `Quote.sub` und `invoicesForQuote`, sonst `projectFee` und alle Rechnungen des Projekts; «bisher» = gestellte Rechnungen (ohne Entwürfe, ohne diese) mit früherem Datum bzw. bei gleichem Datum kleinerer Nummer. Ohne Projekt/Offerte oder Honorar kein Block; Schlussrechnungen nicht (ziehen die Akonti als Positionen ab). **Snapshot**: `Invoice.billingSummary` (JSON, Migration `1787850000_invoice_billing_summary.js`) wird bei jedem Speichern im Editor und beim Wechsel aus dem Entwurf (`freezeOnStatus`: Status-Auswahl, «Als versendet markieren») festgehalten — ein Nachdruck zeigt dieselben Zahlen, auch wenn später Rechnungen dazukommen oder frühere geändert werden. Druck/PDF über `withPrintSummary`/`invoiceForPrint`: Entwürfe immer aktuell gerechnet, gestellte mit Snapshot unverändert, ältere gestellte ohne Snapshot aus den früheren Rechnungen gerechnet. Live-Vorschau (Editor, «Neue Rechnung») rechnet aktuell — dasselbe, was beim Speichern festgehalten wird.
- **Editor**: Positionen als Raster (Beschreibung als mitwachsende Textarea, Zahlenfelder fest breit); Gesamtrabatt erst auf «+ Rabatt auf Gesamtbetrag» (ein gesetzter Rabatt bleibt sichtbar, Rabatt 0 wird als «kein Rabatt» gespeichert); Summen nur im Fuss (Zwischentotal/Rabatt nur mit Rabatt, Netto, MWST, Total) und im PDF.
- **Akonto-MWST** wird mit der Akontorechnung abgerechnet (Vorauszahlung, Art. 40 MWSTG); die Schlussrechnung zieht die Akonti netto ab und belastet MWST nur auf dem Rest.
- **Vertragssumme** aus einer Offerte = netto exkl. MWST (`q.sub`, SIA 1001/1); Vertrag/PDF weisen die MWST separat aus (`contractAmounts`; ältere Verträge mit dem Offert-Brutto werden als netto gelesen).

### Zeiterfassung, Ferien und Saldo (Regeln, Stand 26.11)

- **Eine Quelle:** Soll, Saldo, Ferien und Überstunden rechnet nur [worktime.ts](src/worktime.ts) (`createWorktime(data, heute)`; Tests `worktime.test.ts`, Gleichheit Zeiterfassung ↔ Mitarbeiter in `employees/calc.test.ts`). `timeUtils.ts`, `employees/calc.ts`, «Heute» und die Übersicht-Widgets sind nur Hüllen.
- **Soll:** Wochenstunden × Pensum ÷ 5 an Mo–Fr zwischen Ein- und Austritt; ganze Feiertage frei, Halbtage (`stundenDelta`, gilt für 100 %) und der automatische Vortag (Werktag direkt vor einem ganzen Feiertag, auch Freitag vor einem Samstag-Feiertag; Standard −1 h, einstellbar über `settings.vortagStunden` in Einstellungen → Feiertage, 0 = aus; Büro-Usanz, gesetzlich nicht vorgeschrieben) anteilig nach Pensum. Pensum 0/leer = 100 %.
- **Lohnänderungen** (`employee.lohnVerlauf: { ab, monatslohn }[]`, JSON-Feld, PB-Migration lohn_verlauf): `monatslohn` am Mitarbeiter gilt ab Eintritt, ab jedem Datum der neue Monatslohn (100 %). `calcLohn` rechnet Lohn × Pensum tagesgenau (`lohnImMonat`, Kalendertage, auch zusammen mit Pensumwechsel), «Basis 100 %» = Lohn am letzten angestellten Tag (`monatslohnImMonat`), Überstunden-Stundenlohn mit dem Lohn am Auszahlungsdatum; der 13. Monatslohn gleicht im Dezember auf 1/12 der tatsächlichen Monatslöhne aus. Ein im Lohnlauf übersteuerter Monatslohn ersetzt den Verlauf für diesen Monat.
- **Familienzulagen** im Ein-/Austrittsmonat: Standard voller Monatsbetrag, mit `settings.familienzulagenAnteilig` (Einstellungen → Studio → Lohnkosten) anteilig nach Kalendertagen — je nach Praxis der Familienausgleichskasse.
- **Pensumwechsel** (`employee.pensumVerlauf: { ab, pensum, wochenstunden? }[]`, JSON-Feld): `pensum`/`wochenstunden` am Mitarbeiter sind die Grundwerte ab Eintritt; ab jedem `ab` gilt das neue Pensum, Wochenstunden ohne Angabe laufen weiter (`arbeitszeitAm` in utils.ts). Soll und Halbtage je Tag; Ferienanspruch Tag für Tag (Wochen × Wochenstunden × Pensum ÷ Tage des Monats ÷ 12, ohne Wechsel identisch zur Grundformel); **Lohn tagesgenau anteilig** wie Ein-/Austritt: `calcLohn` nimmt `pensumImMonat` (nach Kalendertagen gewichtetes Pensum, z.B. 1.–15. 80 %, Rest 100 % → 90 % im 30-Tage-Monat); ein im Lohnlauf übersteuertes Pensum gilt für den ganzen Monat (ohne Verlauf). Übersteuerungen (Lohn, Pensum, Bonus) gelten nur für den angezeigten Monat (Monatswechsel leert sie); Storno stellt das Pensum nur wieder her, wenn es vom Monatspensum abwich (sonst rechnete der neue Lauf mit dem gerundeten Pensum statt tagesgenau). Überstunden-Stundenlohn hängt nicht am Pensum (Lohn und Wochenstunden auf 100 %), nur an den Wochenstunden am Auszahlungsdatum. Anzeigen (Personenliste, Zeiterfassung, «Heute») zeigen das heute gültige Pensum.
- **Saldo-Übertrag per Stichtag** (Umstieg von Excel o.ä.; `employee.saldoStichtag`, `saldoUebertragStunden`): vor dem Stichtag zählt nichts (Soll, Ist, Ferien, Absenzen, Ferienanspruch — wie ein zweiter Eintritt), der Überstundensaldo startet mit dem Übertrag; Auszahlungen vor dem Stichtag (ohne Datum: aus früheren Jahren) stecken im Übertrag. Ferienguthaben per Stichtag = `ferienUebertragVorjahr[Stichtag-Jahr]` (kein eigenes Feld; der Jahresabschluss schreibt Jahre vor dem Stichtag nicht). Erfassung im Mitarbeiterformular, auch im Datenimport. Hinweis «sehr grosser Minussaldo» verweist darauf.
- **Saldo** = Ist + genehmigte Absenzen (Teilabsenz mit Von/Bis oder Stunden, sonst Tagessoll; pro Tag höchstens das Tagessoll) + genehmigte Ferien − Soll bis heute; Überstundensaldo seit Eintritt minus Auszahlungen (`uberstundenAbschluss`, Stundenlohn × 12 bzw. 13 ÷ Wochenstunden × 52). Ganztägige Absenz an einem Ferientag: Ferientag nicht bezogen.
- **Ferien:** Anspruch = Wochen (mind. 4, bis zum Jahr des 20. Geburtstags 5; OR 329a) × Wochenstunden × Pensum × Jahresanteil nach Kalendertagen (`monatsAnteilNachEintritt`, wie im Lohn); Bezug = Soll der Ferientage. Änderungsantrag (`originalData`): bis zum Entscheid gelten die bisherigen Daten; ablehnen stellt sie wieder her.
- **Feiertage:** Vorlagen für alle 26 Kantone (`KANTON_FEIERTAGE`, `swissHolidayTemplate(…, kanton)`), Einstellung `settings.kanton` (ui-Blob, Standard ZH; Zürich unverändert wie bis 26.11). Grundlage SECO-Verzeichnis (Art. 20a ArG, Stand 12.12.2024) und BJ; bei Unterschieden nach Bezirk/Konfession (AG, FR, SO, GR, BE …) die Regel des Hauptorts bzw. der Mehrheit. Bewegliche je Jahr: Ostern (Karfreitag −2, Ostermontag +1, Auffahrt +39, Pfingstmontag +50, Fronleichnam +60), Näfelser Fahrt (1. Donnerstag im April, in der Karwoche eine Woche später), Genfer Bettag (Donnerstag nach dem 1. Sonntag im September), Bettagsmontag (Montag nach dem 3. Sonntag im September); bedingte Tage (NE: 2.1./26.12. nur am Montag; AR: kein Stephanstag, wenn Weihnachten auf Mo/Fr fällt) werden je Jahr eingetragen. Halbtage Heiligabend/Silvester und Vortag Auffahrt bleiben in allen Kantonen Büro-Usanz (ausser ein ganzer Feiertag liegt am selben Datum, z.B. GE 31.12.). In Einstellungen → Feiertage ergänzt der Knopf fehlende Jahre (aktuelles + 3); der Kantonswechsel ersetzt auf Wunsch die Vorlagen-Tage ab dem laufenden Jahr (`replaceHolidayTemplate`, eigene Tage und frühere Jahre bleiben).
- **Budget** (`src/budget.ts`, Ansicht StudioBudget): Lohnkosten = 12 Monatsabrechnungen mit `calcLohn` (alle AG-Beiträge, Ein-/Austritt, Rentner, Höchstlohn) statt pauschal 20 %; Fixkosten wiederkehrend aufs Jahr hochgerechnet, beendete nur bis `recurringUntil`; Einnahmen: Offerten nur mit dem noch nicht verrechneten Rest (`invoicesForQuote`, liegt in utils.ts), Entwürfe standardmässig nicht.
- **Rundung:** Vorsteuer pro Beleg auf Rappen (`expenseTax`), Summen = Summe der Zeilen; 13. Monatslohn monatlich 1/12, der Dezember gleicht die Rappen aus (mit den Vorperioden auf 1/12 der tatsächlichen Monatslöhne, auch nach einem Pensumwechsel); Stunden in Anzeigen auf 0.1 mit `roundHours` (worktime.ts, hebt Gleitkomma-Reste wie 3.7499… auf).

## 6. utils.ts — Business-Logik-Bibliothek

[utils.ts](src/utils.ts) ist isoliert und gut testbar. Die wichtigsten Gruppen:

**Kalkulation:**
- `calcSIAHours(baukosten, schwierigkeit, phasen)` — SIA-102-Formel `p = Z1 + Z2/∛B`
- `calcManualHours(phases, roles)` — Stundenansatz × Stunden pro Rolle
- `calcOfficeBenchmarks(projects, timeEntries)` / `estimateEffort(bench, gf, faktor, phasen?)` — Aufwandschätzung aus eigenen Projekten: Stunden je m² GF je Nutzung aus abgeschlossenen Projekten (Status «abgeschlossen», `usage` + `floorArea` gesetzt, ohne Wettbewerb), Median und Bandbreite (ab 5 Projekten 10.–90. Perzentil, sonst min–max), Phasenanteile gemittelt. Gleicher Aufbau wie die ETH Value-Methode (Bezugsgrösse × Kennwert × Anpassungsfaktor, sechs Nutzungen = `PROJECT_USAGES`), aber nur mit eigenen Zahlen — deren Kennwerte sind nicht öffentlich und werden bewusst nicht nachgebaut. UI: [quotes/EffortEstimatePanel](src/views/quotes/EffortEstimatePanel.tsx) im Offerten-Modus «Aufwand», Grundlage bleibt als `quote.estimate`
- `deriveQuoteBudget(linkedQuotes, allQuotes, roles)` — Aggregiert Offerten zu Projekt-Budget (Stunden, Betrag auf Rappen, Stunden und offerierter Betrag je Phase; «Referenz» zählt nicht)
- `quoteBudgetFields(project, linked, quotes, roles)` — die aus Offerten abgeleiteten Projektfelder; **jede** Stelle, die Offerten verknüpft/entkoppelt oder eine verknüpfte Offerte speichert, schreibt damit (Quotes.tsx, ProjectDetail Budget-Dialog, ProjectEditForm). Pauschalprojekte: `budget` = `budgetAmount`, solange Offerten verknüpft sind
- `projectFee(project)` — **die eine Quelle** für das Pauschalhonorar (Akonto %, Akonto-Planer, Schlussrechnung, Kennzahlen, Drucke): mit verknüpften Offerten `budgetAmount` (Hauptofferte + Nachträge), sonst der von Hand gesetzte Pauschalpreis `budget`; Altdaten fallen auf den jeweils anderen Wert zurück. Nie mehr `budget || budgetAmount` direkt lesen
- `invoiceNet(inv)` — Netto einer Rechnung nach Gesamtrabatt (`sub − globalDisc`; robust gegen `subAfterDisc: 0` aus der Cloud). Alle Netto-Kennzahlen (Umsatz, «verrechnet», CRM, Studio-Budget, Abzüge in Schlussrechnungen) rechnen damit, nie mit `sub` (= Zwischentotal vor Rabatt)
- `yearRevenue(invoices, year)` — Umsatz netto: gestellte Rechnungen ohne Entwürfe, nach **Rechnungsdatum**; gleiche Regel für Buchhaltung, Übersicht, «Heute», CSV/PDF-Export
- `calcLohn(emp, monat, spesen, bonus, vorperioden)` — AHV/ALV/BVG/NBU/KTG/Quellensteuer; Eintritt im Monat anteilig (`monatsAnteilNachEintritt`), ALV/NBU bis Höchstlohn 148'200 kumuliert (`hoechstlohnKumuliert`, `HOECHSTLOHN_ALV_UVG`)

**Crypto / Auth:**
- `hashPassword(password, saltHex)` — PBKDF2-SHA-256, 600k Iter (Rundenzahl im Salt, alte Salts 100k), via Web Crypto; `needsPasswordUpgrade(user)`
- `verifyPassword(password, user)` — Constant-Time
- `withHashedPassword(user, password)` — Upgrade legacy → hashed
- `stripCredentials(user)` — Entfernt `password`, `passwordHash`, `passwordSalt`

**Sicherheit:**
- `sanitizeHtml(html)` — Allowlist (`<p>`, `<br>`, `<b>`, `<a>`, …), blockiert `<script>`, `javascript:`, `on*`-Handler; Inhalt nicht erlaubter Elemente wird vor dem Hochziehen ebenfalls bereinigt, `<script>/<style>/<svg>/<iframe>` … samt Inhalt entfernt, Kommentare weg (Tests `utils.sanitize.test.ts` mit jsdom)

**Druck-Trigger:** `getCurrentWebviewWindow().print()` (Tauri WebView) oder Fallback `window.print()` (Browser).

Margins konfigurierbar über `settings.pageMargin{Top,Bottom,Left,Right}`.

**Dokument-Design (Einstellungen → Erscheinungsbild, [DocDesignSettings.tsx](src/components/DocDesignSettings.tsx)):** `settings.docDesign` (Schriften, Farben, Folgeseiten-Ränder, eigenes CSS) und `data.docAssets` (hochgeladene Schriften + Briefpapier als Data-URL). Neue Dokumente: Variablen statt fester Farben/Schriften verwenden. Briefpapier: PDF wird beim Upload mit pdf.js gerastert (`print/docAssets.ts`), Ebenen hinter dem Inhalt (`LetterheadLayers`). **Seitenumbruch:** [print/paginate.ts](src/print/paginate.ts) setzt Abstandselemente, damit Folgeseiten oben/unten Rand haben (die Druckansicht läuft mit `@page{margin:0}`; WKWebView wiederholt weder `position:fixed` noch `box-decoration-break` noch Tabellenköpfe). Gemessen mit WKWebView/NSPrintOperation: das Blatt muss im Druck exakt `width:210mm` haben, sonst skaliert WebKit (744 px Druckbreite). Der QR-Zahlteil ist vom Design ausgenommen (Arial per Norm) und steht immer am unteren Blattrand (2 mm Luft, sonst druckte Chromium eine leere Zusatzseite): auf eigener Seite oder unten auf der Seite, auf der er ganz Platz hat (`qrPage` und damit eine Seite ohne Folgeseiten-Briefpapier nur, wenn der Zahlteil allein auf der Seite steht; ein Hinweis statt Zahlteil — Gutschrift, Betrag 0, keine IBAN — bekommt keine eigene Seite). Abstände misst `paginate` nach (aufgehobenes Zusammenfallen der Ränder); ein Block mit `break-inside: avoid`, der höher als eine Seite ist, bekommt `auto` (sonst schob Chromium ihn beim Drucken als Ganzes weiter und alle Abstände lagen daneben). Mehrzeiliger Freitext im Druck über `PrintText` (docs/PrintText.tsx): jede Zeile, bei sehr langen Absätzen jeder Satz, ein eigener Block — ein Block höher als eine Seite lief sonst über die Ränder; Hintergrund/Randlinie einer Box je Zeile (`lineStyle`), lange Wörter/URLs umbrechen; kein Lookbehind-Regex (älteres WebKit).
**Cloud:** `docAssets`-Collection (Migration `1787760000_doc_assets.js`, Schreibrecht `settings`), `docDesign` im `ui`-JSON von `studioSettings`. **Lokal:** localStorage fasst in WKWebView nur ~5,2 Mio. Zeichen (gemessen) — `checkLocalBudget()` verweigert Uploads darüber.

## 9. Updater-Pipeline End-to-End

```
release.sh (lokal, manuell aufgerufen)
  ├─ liest VERSION aus tauri.conf.json, package.json und Cargo.toml (Mismatch → Exit)
  ├─ Lädt Private Key aus ~/.tauri/rapport_updater.key (kein Passwort)
  ├─ npx tauri build --target universal-apple-darwin   (mit TAURI_SIGNING_PRIVATE_KEY env;
  │    braucht `rustup target add aarch64-apple-darwin x86_64-apple-darwin`; RELEASE_TARGET=native = alter Build)
  ├─ findet .app.tar.gz + .sig in src-tauri/target/universal-apple-darwin/release/bundle/macos/
  └─ schreibt latest.json (Repo-Root) mit version, signature, url, pub_date —
       Universal: darwin-aarch64 UND darwin-x86_64 zeigen auf dasselbe Bundle
     └─ url zeigt auf Gitea Release Asset (manuell hochzuladen)

User (manuell):
  ├─ Gitea-Webinterface: Release mit Tag <VERSION> (ohne v-Prefix) erstellen
  ├─ .app.tar.gz (+ optional .dmg) hochladen
  └─ git add latest.json && git commit && git push origin main

App-Start (in jeder installierten Version):
  ├─ UpdateNotifier.tsx: setTimeout 1.5s → checkForAppUpdate({ silent: true })
  ├─ Tauri-Plugin GET https://git.kgva.ch/karim/RAPPORT/raw/branch/main/latest.json
  ├─ Verifiziert Signature gegen pubkey aus tauri.conf.json (Minisign)
  ├─ Vergleicht latest.json.version mit getVersion()
  └─ Wenn neuer → Modal mit "Installieren / Später / Diese Version überspringen"

Installation:
  ├─ update.downloadAndInstall(onProgress)  // lädt von url in latest.json
  └─ relaunch() (via plugin-process)
```

**Updater-Komponenten im Frontend:**
- [src/utils/updater.ts](src/utils/updater.ts) (49 Z.) — Wrapper, kapselt Skip-Logik in `localStorage`

## 10. Build & Release-Workflow

**Versionen nach Datum (seit Beta 26.11):** `Jahr.Monat.Nachtrag` — `26.11.0` ist «Beta 26.11», ein zweites Release im selben Monat `26.11.1` («Beta 26.11.1»). Drei Zahlen, weil der Updater semver vergleicht (26.11.0 > 0.8.3, alte Installationen bekommen das Update). Angezeigt wird überall `versionLabel()` aus [changelog.ts](src/changelog.ts) (Sidebar, Login, «Über Rapport», Changelog, Update-Dialoge); 0.x-Versionen heissen dort weiter «Alpha». Das macOS-Fenster «Über RAPPORT» (App-Menü) setzt [lib.rs](src-tauri/src/lib.rs) selbst: Version über `version_label()` (gleiche Regel wie `versionLabel`, beide gleich halten), darunter Copyright/Entwickler aus `bundle.copyright`/`bundle.publisher` in tauri.conf.json. Der App-Name ist «RAPPORT» (`productName`/Fenstertitel in tauri.conf.json, bis 0.8.3 «RAPPORT PRE-RELEASE»); der `identifier` bleibt unverändert, sonst gingen localStorage und Berechtigungen bestehender Installationen verloren. `src/changelog.test.ts` prüft, dass `LATEST_VERSION` = package.json-Version ist und einen Changelog-Eintrag hat.

**Versions-Bump betrifft drei Dateien — alle drei müssen synchron sein:**
1. [package.json](package.json) → `"version"`
2. [src-tauri/tauri.conf.json](src-tauri/tauri.conf.json) → `"version"`
3. [src-tauri/Cargo.toml](src-tauri/Cargo.toml) → `[package] version`

**Zusätzlich für jeden Release:**
4. [src/changelog.ts](src/changelog.ts) → Changelog-Entry oben in `CHANGELOGS`
5. [src/changelog.ts](src/changelog.ts) → `LATEST_VERSION` anheben (steuert Sidebar-Anzeige, Login-Fusszeile und den `rapport_changelog_seen`-Vergleich)

> `release.sh` prüft 1–3 und bricht bei Abweichung ab; 4+5 prüft es nicht.

## 12. Wo es weh tut — Realistische Schwachstellen

1. **Grosse Views** — ProjectDetail, Time, Invoices und Employees sind in Unterordner aufgeteilt (Einstiegsdatei je ~250–350 Zeilen, nur Struktur, Vorher/Nachher-Screenshots gleich). Noch gross: [StudioBudget](src/views/StudioBudget.tsx), [Dashboard](src/views/Dashboard.tsx), [Protocols](src/views/Protocols.tsx), [DataImport](src/views/DataImport.tsx), [Quotes](src/views/Quotes.tsx) (~800–1000 Zeilen).
2. **App.tsx ist ~420 Zeilen** und hält noch Login/Cloud-Setup (nutzt `save`/`setData`), View-Routing, Print-Routing und die Layout-Hülle. Der Daten-State liegt in `hooks/useStudioData.ts`; ausgelagert sind ausserdem Sidebar, Changelog/Über, globales CSS, Navigation, Erscheinungsbild und Rechte-Ableitung. Jede Änderung an App.tsx ist hochriskant — sie betrifft alles.
3. **Inline-Styles ohne Konvention** — Spacing ist über das Projekt verstreut; Farben laufen über Theme- und Bedeutungsvariablen (siehe §11), Reste von Hex-Werten stehen noch in Template-Strings.
4. **Modal-State chaotisch** — manche Views haben `{type,id}`, andere mehrere `useState`. Kein zentraler Manager.
5. **Wenige Tests.** Vitest (`npm test`) deckt QR-Referenz, Lohn, SIA-Honorar, Nummernformate, Passwörter, Datenordner/Dateiablage und die Datenprüfung ab. Keine UI-Tests, kein Rust-Test. Ablauf Offerte → Projekt → Rechnungen (Summen, Budget, Akonto/Schluss, Nummern) in [offerteRechnungFlow.test.ts](src/views/invoices/offerteRechnungFlow.test.ts), Druck-Summen in `print/docs/*.test.tsx`.
6. **TypeScript seit der Migration (siehe TYPESCRIPT-MIGRATION.md).** Die Typen des Datenmodells stehen in [src/types.ts](src/types.ts); ältere Datensätze sind aber oft unvollständig, deshalb sind viele Felder optional. Ein Schema-Refactor braucht trotzdem eine Migration in `storage/migrations.ts`.
7. **Error-Boundary** ([ErrorBoundary.tsx](src/components/ErrorBoundary.tsx)) um die Ansichten (Ansichtswechsel setzt zurück), um die Druckansicht und ganz aussen in main.tsx. Ein Fehler zeigt eine Meldung statt weissem Bildschirm, «Fehlertext kopieren» liefert Stack, Ansicht und Version für den Support — behoben ist er damit nicht.
8. **Datenprüfung nur grob** ([validate.ts](src/storage/validate.ts)): oberste Ebene, `settings` und die Unterlisten aus `NESTED_LISTS`; einzelne Felder in Einträgen werden nicht geprüft.
9. **Keine CI**, keine Pre-Commit-Hooks. `npm run lint` und `npm run typecheck` muss man sich selbst merken (beide sind sauber).
10. **Updater nur für macOS** — `release.sh` baut Universal (Apple Silicon + Intel); Windows/Linux haben keinen Build und kein Update.

## 14. Offene Fragen / Nicht-Validiertes

- Bild-Uploads (Belege, Logo, Pinnwand, Avatar, Dokument-Design) liegen in der App als Data-URL in `data`; Fotos werden verkleinert (Belege 1600 px, Pinnwand 1200 px, Avatar 256 px). Im Datenordner liegen sie als eigene Dateien unter `Dateien/` (file-assets.ts), in der Cloud in PocketBase-Dateifeldern (pocketbase-files.ts, §3); Belege sind in beiden Fällen auch in der App nur Verweise (useAttachment). Im lokalen Modus (~4,8 Mio. Zeichen Budget, `LOCAL_STORAGE_BUDGET`) prüfen Belege, Logo und Dokument-Design vorher `checkLocalBudget`.
- PDF-Export: aktuell nur `window.print()` → User-PDF-Dialog. Kein direkter File-Save.
- Multi-User-Workflow: `users[]` in `data`, aber nur ein Browser-localStorage → keine echte Mehrfachnutzung.
